## 확인한 바이너리와 진입 경로

`Store/image.img`는 FAT16 게임 데이터 디스크다. Windows 자체의 설치 여부를 확인하거나 Windows를 실행한 것은 아니다. `tools/g3_image.py`는 원본을 읽기 전용으로 열어 2,655개 파일과 14개 디렉터리를 열람한다. 7-Zip이 추출한 EXE, DLL, 동영상과 바이트 단위로 비교했다.

`G3Launch.exe`와 `alpha.dll`은 PE 머신 값 `0x014c`인 x86 바이너리다. 핵심 코드는 `alpha.dll`에 있다. DirectDraw, DirectSound, WinMM, MSACM32 및 Windows API를 참조한다. 인접한 MFC 디버그 DLL이 게임 엔진의 직접 의존성이라는 의미는 아니다. 실제 import 목록은 생성된 분석 보고서에 있다.

다음 주소는 현재 파일의 기본 이미지 주소 `0x10000000`을 적용한 정적 가상 주소다. Capstone의 선형 디스어셈블 결과이며, 코드 안의 인라인 데이터나 분기 타깃은 후속 제어 흐름 분석이 필요하다.

| 주소 | 관찰한 근거와 현재 해석 |
| --- | --- |
| `0x100010B0` | export `_DoTheGame@4`. 초기화, 인자 처리, 실행 루프, 종료 정리를 호출한다. |
| `0x10001100` / `0x10001110` | export `_PauseApp@0` / `_ResumeApp@0`. `0x1011FB74`에 1 / 0을 기록한다. |
| `0x10001120` | export `_KillGame@0`. 비어 있지 않은 핸들에 대해 import 함수를 호출한다. |
| `0x10004B00` | 파일 로더. `.idx` 경로 생성과 인덱스 검색, 개별 파일을 여는 경로가 있다. 실행 옵션별 우선순위는 미확정이다. |
| `0x10004D65` 이후 | 파일명 9바이트, 묶음명 13바이트, 32비트 값 두 개를 읽는다. IDX 레코드 형식의 코드 근거다. |
| `0x10005670` | 로그에 `CfreadDec` 이름이 남아 있다. `0x100056F8`의 `not bl`로 읽은 바이트를 반전한다. |
| `0x1009D7E0` | `Chars\\%04d.chr`를 연다. 이름 24 / 24 / 10바이트를 반전 읽기 함수로 읽는다. |
| `0x100D6440` | 초기화 후 상태값을 사용해 `0x10006090`를 반복 호출한다. 상태별 실행의 후보이며 의미는 아직 복원하지 않았다. |

스크립트 `tools/analyze_game.py`로 재생성되는 자료:

- `reverse/analysis.json`: import/export, 해시, 자원 참조 주소, 리소스 목록, 복원 텍스트와 인물명.
- `reverse/alpha.dll.asm`, `reverse/G3Launch.exe.asm`: 주소, 명령어, 문자열/import 주석.
- `reverse/image-manifest.json`: FAT 파일 목록. `tools/g3_image.py --manifest`로 생성한다.

원본 및 대량의 생성 자료는 Git 추적 대상에서 제외했다.

## 복원한 데이터 형식

### IDX / PAK

파일 앞의 little-endian `uint32`가 레코드 수다. 레코드는 정확히 30바이트다.

| 오프셋 | 길이 | 의미 |
| --- | --- | --- |
| 0 | 9 | NUL 종료 리소스 파일명 |
| 9 | 13 | NUL 종료 묶음 파일명 |
| 22 | 4 | 묶음 내 시작 위치 |
| 26 | 4 | 묶음 내 마지막 바이트 위치, 포함 범위 |

7개 인덱스의 총 5,622개 레코드가 묶음 범위 안에 있음을 확인했다. `Snd.idx`에는 같은 리소스 이름이 여러 묶음에 반복된다. 파서는 순서를 보존한다. 조회 우선순위는 별도 복원이 필요하다.

개별 파일과 묶음의 내용을 비교한 결과:

| 인덱스 | 레코드 수 | 비교 가능한 개별 파일 | 바이트가 같은 파일 |
| --- | ---: | ---: | ---: |
| BGRs | 370 | 0 | 0 |
| Btls | 894 | 894 | 745 |
| Chars | 622 | 622 | 578 |
| Chps | 176 | 176 | 165 |
| Flds | 458 | 458 | 444 |
| Obss | 992 | 11 | 0 |
| Snd | 2,110 | 0 | 0 |

차이는 분석 실패로 단정하지 않았다. 커스텀판의 개별 파일과 묶음이 서로 다른 버전일 수 있으며, 어느 쪽을 실제로 사용하는지는 로더 경로에 따라 달라진다. 현재 표시용 자산은 개별 파일이 없는 BGRs 묶음을 기준으로 한다.

### 텍스트와 인물명

`.DLG`, `.CLG`, `.FLG`, `.ELG`에서 다음 형식을 확인했다.

1. 문자열 수 `uint16`, 문자열 데이터 길이 `uint16`.
2. 문자열 데이터 시작점 기준의 `uint16` 오프셋 배열.
3. 각 문자열의 바이트를 `XOR 0xFF`한 데이터. 저장 상태의 `0xFF`가 문자열 종료 바이트다.
4. 반전 후 CP949로 해석하면 한글이 복원된다. `/m`, `/n` 등의 제어 코드는 그대로 보존한다.

개별 텍스트 파일 762개 중 751개에서 10,811개 문자열을 엄격한 CP949 해석으로 읽었다. 나머지 11개는 헤더 길이 미만으로 기록되어 오류 목록에 남겼다. 묶음에만 있는 대사를 전부 해석했다는 의미는 아니다.

`.CHR`의 시작 24 / 24 / 10바이트는 반전된 이름 영역이다. 628개 개별 파일을 조사했으며 한 파일(`0213.CHR`)은 이 영역의 CP949 해석에 실패했다. 실패한 바이트를 임의로 대체하지 않았다. 이름 뒤 필드의 역할, 전투 수치 및 체크섬은 아직 확정하지 않았다.

`G3.pak`는 범용 데이터 묶음이 아니라 `RIFF ... AVI `로 시작하는 동영상이다. `.BGM`의 조사 표본은 RIFF WAVE / MS ADPCM 형식이다. 모든 PAK/BGM이 같은 코덱이라는 가정은 하지 않는다.

## 작성한 홈브루 코드

`homebrew/source/g3_formats.c`는 원본 IDX와 텍스트 테이블을 읽는 공용 C 코드다. 정렬된 구조체 캐스팅을 사용하지 않고 little-endian 값을 명시적으로 읽는다. 범위, 파일명, 종료 바이트와 버퍼 용량을 검사한다.

`homebrew/source/main.c`는 libnx 프레임버퍼에 복원 배경을 표시하는 리소스 뷰어다. L/R 또는 방향키로 이동하고 ZL/ZR로 10개씩 이동하며 +로 종료하도록 작성했다. 현재 게임 루프, 전투, 대사 이벤트를 실행하는 코드가 아니다.

`tools/prepare_assets.py`는 BGRs의 370개 항목을 해석해 `dist/switch/g3nx/g3nx.assets`로 변환했다. 원본은 보존하고 뷰어 사본만 최대 1,040×624 RGBA로 줄인다. GIF는 첫 프레임만 사용한다. 원본 해상도, 형식과 해시는 옆의 JSON에 기록한다. 표시용 파일의 크기는 453,261,404바이트다. 이것은 실행 파일이 아니며 SD 카드에 복사하는 것만으로 게임이 실행되지는 않는다.

변환 파일 형식은 새로 정의한 `G3NXRAW1`이며 원본 게임의 포맷으로 주장하지 않는다. 헤더 16바이트, 항목당 32바이트의 디렉터리, RGBA 데이터 순서다. 한 번에 화면용 버퍼 약 2.6MB만 읽는다.

## 검증과 현재 제약

- MSVC `/W4 /WX`로 공용 C 로더 DLL을 빌드했다.
- Python 참조 구현과 C 구현을 5,622개 IDX 레코드 및 10,811개 문자열에 대해 비교했다.
- 표시용 자산 370개를 C 로더로 읽었고, 대표 이미지의 전체 RGBA 바이트를 Pillow 변환 결과와 비교했다.
- 잘못된 버퍼 2,000개, 손상된 디렉터리 범위, 버퍼 용량 부족을 검사했다.
- 회귀 검사 7개가 모두 통과했다.
- Android NDK Clang으로 공용 C 파일을 ARM64 오브젝트로 컴파일했다. Switch용 링크/앱 검증이 아니라 공용 코드의 ARM64 컴파일 확인이다.

이 PC에서 기본 위치의 devkitPro/devkitA64를 찾지 못했다. 공식 패키지 저장소의 `dkp-libs.db`와 `dkp-windows.db` 요청이 HTTP 403을 반환했다. `devkita64-rules`는 유효한 공식 빌드 규칙이지만 컴파일러, libnx 및 NRO 도구를 포함하는 완전한 개발 환경은 아니다.

후속 작업에서 사용자가 설치한 `OldGame/switchTool/devkitPro/msys2`의 패키지 캐시를 확인했다. MSYS의 `/opt/devkitpro` 매핑에 한글 경로가 깨져 있어 설치 위치에서는 도구를 찾지 못했다. 캐시의 공식 devkitA64 r30 / GCC 16.1.0, libnx 4.12.0, switch-tools 1.13.1과 관련 패키지를 현재 작업 폴더의 `.toolchain/local/opt/devkitpro`로 추출했다. 기존 설치와 fstab은 변경하지 않았다.

`tools/build_switch.py`는 MSYS를 거치지 않고 Windows 도구를 직접 호출한다. `main.c`와 공용 로더를 경고를 오류로 처리하여 컴파일하고 libnx와 링크한 뒤 NACP 및 NRO를 생성했다. ELF64/AArch64, NRO0/ASET 헤더, 페이지 정렬된 세그먼트 범위와 앱 제목을 검사한다. 배포 폴더는 `dist/switch/g3nx`이며 해시는 `build-report.json`에 기록한다.

**NRO 빌드 및 파일 구조 검증은 완료했다. 실기 구동, 프레임 속도, 입력 동작은 여전히 미검증이다.** 뷰어의 실제 동작을 확인하고 이후 게임 동작을 복원해야 한다.

## 후속 복원 범위

다음 단계는 원본 로더의 개별 파일/묶음 우선순위를 확정하고, 에피소드 상태 전이와 CPR/FLD/BTL 이벤트 명령을 코드 참조와 대조하는 것이다. 이후 OBS/OBT 스프라이트 및 맵, 경로 탐색과 전투 규칙, ADPCM/동영상, 대사 렌더링, 저장 형식과 체크섬을 순차 복원해야 한다. 현재 도구는 그 작업에 쓸 정적 주소와 데이터를 보존한다.

기존 Windows 바이너리를 ARM64로 단순 재링크하는 방식은 구현하지 않았다. 일반 게임 플레이 이식 완료로 간주할 수 있는 근거는 아직 없다.
